\section{Feature Audit Notes}\label{app:signals}

The four active modules are retained to make historical calculations auditable,
not because their internal thresholds are validated invariants.  Each module
maps an address's observed transactions to $[0,1]$ using hand-authored
transformations of amount, counterparty graph, transfer direction/velocity, and
timing.  Cross-platform correlation is inactive in the single-chain corpus.

For a confirmatory study, each component must be rewritten as a preregistered
feature contract containing: data plane; unit and window; expected direction;
legitimate twins; missingness behavior; leakage boundary; proposed mechanism;
and an observation that would falsify that mechanism.  Feature code and graph
state must be fitted only on training intervals/components.  Thresholds and
weights must be frozen before opening the final holdout.

No feature alone or in combination should be interpreted as fraud.  In
particular, low-value, bursty, regular, hub-like, circular, or rapidly forwarded
transactions all have ordinary service, exchange, treasury, liquidity, or
automation explanations.  Conversely, a malicious controller can use slow,
low-volume, stochastic, or off-chain strategies that avoid these descriptors.
